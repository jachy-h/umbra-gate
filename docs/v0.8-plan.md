# v0.8 设计方案：可配置模型优先级与 Provider 凭据归属

## 目标

v0.8 调整 Link 的两个配置边界：

1. 每个 Provider 节点拥有一份**有序、可编辑**的模型优先级列表；请求会完全按该列表依次尝试模型。
2. API Key 只归属 Provider；Link 不保存、不传递，也不覆盖 Provider 的 API Key。

## 非目标

- 不根据 Provider 的 `models` 列表自动推导运行时回退顺序。
- 不在 Link 中支持按节点覆盖 API Key。
- 不改变 Link 的 Provider 链顺序、协议兼容性校验或格式转换规则。

## 核心术语

- **Provider 链**：Link 中的 Provider 节点有序列表。只有当前节点的所有模型优先级均失败后，才进入下一个节点。
- **模型优先级**：一个 Provider 节点内有序的模型候选项。候选项可引用客户端请求中的模型，也可指定固定模型。
- **接收到的模型**：客户端请求体 `model` 字段的值。它是模型优先级中的特殊候选项，而非隐式的固定第一项。

## 配置模型

### Link 节点

`ChainEntry` 改为保存有序的 `model_priorities`：

```go
type ModelPriority struct {
    Source string `json:"source"` // "request_model" | "fixed_model"
    Model  string `json:"model,omitempty"`
}

type ChainEntry struct {
    ProviderID      string          `json:"provider_id"`
    Protocol        string          `json:"protocol"`
    RetryCount      int             `json:"retry_count"`
    ModelPriorities []ModelPriority `json:"model_priorities"`
    Rules           Rules           `json:"rules,omitempty"`
    ValidationOK    *bool           `json:"validation_ok,omitempty"`
    ValidationError string          `json:"validation_error,omitempty"`
    ValidatedAt     time.Time       `json:"validated_at,omitempty"`
    SupportedFormats []string       `json:"supported_formats,omitempty"`
}
```

`source` 的约束：

| Source | `model` | 含义 |
| --- | --- | --- |
| `request_model` | 必须为空 | 使用客户端本次请求的 `model` 值。 |
| `fixed_model` | 必须为非空字符串 | 使用此处配置的固定上游模型。 |

每个节点至少应有一个模型优先级。`request_model` 在同一节点中最多出现一次，以避免对同一个动态模型作重复尝试；它可以处于任意位置，也可以不出现。

例如，Provider 1 的顺序可以是：

```json
{
  "provider_id": "provider-1",
  "model_priorities": [
    { "source": "request_model" },
    { "source": "fixed_model", "model": "模型1" },
    { "source": "fixed_model", "model": "模型2" }
  ]
}
```

Provider 2 有自己的独立顺序，例如：

```json
{
  "provider_id": "provider-2",
  "model_priorities": [
    { "source": "fixed_model", "model": "模型A" },
    { "source": "request_model" },
    { "source": "fixed_model", "model": "模型B" }
  ]
}
```

这两个节点组合后的实际尝试顺序为：

```text
Provider 1 / 接收到的模型
→ Provider 1 / 模型1
→ Provider 1 / 模型2
→ Provider 2 / 模型A
→ Provider 2 / 接收到的模型
→ Provider 2 / 模型B
```

因此“接收到的模型”不是任何 Provider 的默认第一优先级；它仅在用户将该特殊项放入对应位置时使用。

### API Key

API Key 仅保留在 `Provider.APIKey` 和 `providers.api_key` 中。`ChainEntry` 不包含 `ApiKey` 字段，Link API 与数据库也不保存该值。

Provider 读取接口仅返回：

```json
{
  "has_api_key": true
}
```

而绝不返回 API Key 明文。

## 路由语义

路由器依次遍历 Provider 链；在每个 Provider 内，按 `model_priorities` 的配置顺序解析并尝试模型。

伪代码：

```go
for _, entry := range link.Chain {
    provider := loadEnabledProvider(entry.ProviderID)

    for _, priority := range entry.ModelPriorities {
        model, ok := resolveModel(priority, requestModel)
        if !ok { // 例如 request_model 但客户端没有传 model
            continue
        }
        if alreadyTried(model) {
            continue
        }

        for attempt := 0; attempt <= entry.RetryCount; attempt++ {
            result := forward(provider, model)
            recordAttempt(provider, model, result)
            if result.Success {
                return result
            }
        }
    }
}
return allProvidersFailed
```

规则：

- `request_model` 在客户端未传 `model` 时无法解析，跳过该项。
- 同一 Provider 内解析后得到相同模型名的候选项只尝试一次，避免配置重复带来无意义请求。
- `retry_count` 的语义为**同一模型的额外重试次数**；模型优先级切换不是重试。
- 当前节点全部模型均失败，才进入下一 Provider 节点。
- Provider 的 `models` 是管理页的模型目录、输入提示和测试候选来源，不参与隐式运行时回退。
- 如果所有模型优先级均无法解析或全部失败，返回现有的全链路失败错误。

请求日志继续记录实际使用的 `provider_id`、Provider 名称和模型，因此可以从请求详情还原完整的回退路径。

## API 和校验

### Link 创建和更新

Link 请求体使用：

```json
{
  "chain": [
    {
      "provider_id": "provider-1",
      "model_priorities": [
        { "source": "request_model" },
        { "source": "fixed_model", "model": "模型1" }
      ],
      "retry_count": 0
    }
  ]
}
```

服务端校验：

- `model_priorities` 不能为空。
- 每个候选项的 `source` 必须为 `request_model` 或 `fixed_model`。
- `request_model` 不得携带 `model`，且单节点最多一个。
- `fixed_model` 必须携带去除首尾空格后的非空 `model`。
- 拒绝 `chain[].api_key`，返回 400：`API key must be configured on the provider`。
- 保留现有 Provider 存在性、启用状态、协议和格式兼容性校验。

### Provider API Key

新增专用写入接口：

```http
PUT /admin/providers/:id/api-key
Content-Type: application/json

{ "api_key": "sk-..." }
```

行为：

- 仅更新该 Provider 的 `api_key`。
- 返回脱敏后的 Provider（`api_key` 为空，`has_api_key` 反映配置状态）。
- Provider 不存在返回 404。
- Provider 的普通创建/编辑接口仍可写入 API Key；编辑请求中省略 `api_key` 时必须保留原有密钥。
- Provider 列表和单 Provider 查询始终不返回明文密钥。

## 数据库迁移

`proxy_link_providers` 改为：

```sql
CREATE TABLE proxy_link_providers (
    link_id TEXT NOT NULL,
    position INTEGER NOT NULL,
    provider_id TEXT NOT NULL,
    protocol TEXT NOT NULL DEFAULT '',
    retry_count INTEGER NOT NULL DEFAULT 0,
    model_priorities_json TEXT NOT NULL DEFAULT '[]',
    rules_json TEXT NOT NULL DEFAULT '{}',
    validation_ok INTEGER,
    validation_error TEXT NOT NULL DEFAULT '',
    validated_at DATETIME,
    supported_formats_json TEXT NOT NULL DEFAULT '[]',
    PRIMARY KEY (link_id, position),
    FOREIGN KEY (link_id) REFERENCES proxy_links(id) ON DELETE CASCADE
);
```

迁移步骤必须在事务中完成：

1. 创建不含 `fallback_model` 和 `api_key` 的新表。
2. 读取旧表记录。
3. 对每条记录生成 `model_priorities_json`：
   - 若旧 `fallback_model` 非空：`[{"source":"request_model"},{"source":"fixed_model","model":"旧值"}]`。
   - 若旧 `fallback_model` 为空：`[{"source":"request_model"}]`。
4. 复制其他非密钥字段。
5. 删除旧表并重命名新表。
6. 提交事务。

旧 Link 节点中的 API Key 不迁移，确保升级后数据库中不再有 Link 级凭据。迁移需具备幂等性，并通过表结构检测或显式 schema version 保证只执行一次。

## 前端设计

### Link 编辑器

每个 Provider 节点显示可排序的模型优先级列表：

```text
Provider: OpenCode Go

模型优先级
1. 接收到的模型                 [上移] [下移] [删除]
2. 固定模型：模型1               [上移] [下移] [删除]
3. 固定模型：模型2               [上移] [下移] [删除]

[+ 添加“接收到的模型”]  [+ 添加固定模型]
```

交互规则：

- “接收到的模型”与固定模型均可移动；不存在固定首项。
- “接收到的模型”已经存在时，禁用或隐藏再次添加入口。
- 固定模型输入优先使用当前 Provider 的 `models` 作为可搜索候选，同时允许手动输入。
- 移除旧的单个 `Fallback Model` 输入框。
- 移除 Link 中所有 API Key 输入框、覆盖逻辑和标识。
- Link 预览按 Provider 与其模型优先级展示，而不只显示 Provider 名称。

### 从 Link 配置 Provider API Key

选择某个 Provider 后：

- 若 `has_api_key` 为 `false`，在该节点显示按钮：`配置 {Provider 名称} Provider`。
- 点击按钮打开独立 Modal：

```text
配置 OpenCode Go Provider
API Key: [密码输入框]

取消  保存
```

- 保存调用 `PUT /admin/providers/:id/api-key`。
- 成功后刷新 Provider 数据但不重置当前 Link 表单；该节点变为“已配置 API Key”，可提供“修改 API Key”入口。
- Link 仍允许使用不需要密钥的 Provider；没有 API Key 不作为 Link 保存的硬性阻断条件。

### Provider 管理页

Provider 列表继续显示所有 Provider。API Key 列只显示：

- `未设置`；或
- `••••••••`。

不显示、回填或复制明文 API Key。通过 Link 编辑器配置成功后，返回 Provider 管理页即可看到相应 Provider 的掩码状态。

## 链路测试

链路测试增加可选测试模型参数：

```http
POST /admin/links/:id/test

{ "model": "gpt-5" }
```

测试时按每个节点的 `model_priorities` 解析顺序执行：

- `request_model` 使用测试模型；
- `fixed_model` 使用配置模型；
- 未提供测试模型时跳过 `request_model`，仍测试所有固定模型。

测试结果记录实际 Provider、模型、格式和失败原因；格式能力的聚合规则保持现有实现。

## 测试与验收

### 后端

- Provider 1/Provider 2 使用不同可配置模型优先级时，实际转发顺序与 JSON 数组顺序一致。
- `request_model` 位于中间或末尾时，按其位置而非默认首项尝试。
- Provider 2 不继承 Provider 1 的最后一个模型，而是使用自身列表。
- 同一 Provider 的重复解析模型只调用一次。
- `retry_count` 只重试当前模型，不改变模型优先级顺序。
- Link API 拒绝 `chain.api_key`。
- 数据库迁移正确转换旧 `fallback_model`，并永久删除旧 Link API Key。
- Provider API Key 写入、保留、脱敏和 404 行为正确。

### 前端

- 用户可添加、删除、上移和下移任意模型优先级项。
- `request_model` 最多只能添加一次，但可移动到任意位置。
- 选择没有 API Key 的 Provider 时出现“配置 xxx Provider”按钮。
- Modal 保存后，当前 Link 表单不丢失且 Provider 密钥状态立即更新。
- Link 编辑器不再包含 API Key 或 API Key override 字段。
- Provider 列表仅显示密钥配置状态，不显示明文。
